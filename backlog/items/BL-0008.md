## Context

Without an explicit `serviceInterface`, the library takes the "first suitable" interface from `Type.GetInterfaces()`. That rule is fragile in several ways:

- The order of `GetInterfaces()` is not guaranteed.
- The candidates include interfaces inherited from base classes. `DerivedSvc : BaseSvc, IDerived` (where `BaseSvc : IParent`) was registered as `IParent`.
- The namespace filter is a heuristic with a known hole. It removes `System.*` but not the root `System` namespace, so `Money : IEquatable<Money>, IMoney` is registered as `IEquatable<Money>`.
- When filtering removes everything, it falls back to the first interface of any kind, which can be `IDisposable`.

The current docs describe all of this, but the behaviour is still surprising and order-dependent.

## Scope

- Only consider interfaces the class declares itself, not ones inherited through its base class.
- Exclude framework interfaces with an explicit rule. That means the root `System` namespace too, not only `System.*`, or alternatively an explicit list.
- Exactly one candidate: use it. More than one: report an "ambiguous interface, specify serviceInterface" validation error. None: report the existing "no interface" problem.
- Remove the "first interface of any kind" fallback.

## Acceptance criteria

- [ ] A class with one declared, non-framework interface registers as that interface regardless of base classes.
- [ ] `IEquatable<T>`, `IComparable<T>` and `ICloneable` are never chosen automatically.
- [ ] Two or more candidates without `serviceInterface` produce a clear validation error.
- [ ] Existing fixtures that relied on the fallback are updated: `ServiceWithOnlyIDisposable`, `ServiceWithOnlySystemInterfaces`, `ServiceWithMultipleInterfaces`.
- [ ] `dotnet build` and the full test suite pass.
- [ ] README and `docs/` updated: API-Reference "Interface selection", Troubleshooting, Best-Practices.

## Decision points

- "Declared" means not implemented by the base class. An interface that inherits from another declared interface (`IChild : IParent`) needs a rule too; suggest picking the most derived one.
- Whether ambiguity is always an error, or an error only in fail-fast mode.
- Whether a non-breaking stopgap should ship first: just fix the root `System` namespace filter in a patch release.
