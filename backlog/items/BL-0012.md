## Context

The example exists to show the layered registration pattern: `AssemblyReference` per project, chained `AddDemoX()` bootstrap methods, and `[AutoRegister]` classes spread across layers. Most of its code has nothing to do with that:

- `UserService` has seven CRUD and search methods with `Task.Delay`, logging and email-uniqueness validation.
- The DTOs and the `User` model carry data-annotation attributes that nothing validates.
- `IUserService` has an XML doc on every member.

Readers have to wade through this to find the four or five classes that matter.

## Scope

- Keep all five layers, one `[AutoRegister]` service per layer, the `AssemblyReference` and bootstrap pattern, and the lifetime demo in `Demo.ConsoleApp`.
- Cut `IUserService` and `UserService` down to create and get-by-ID (plus list, if the scenario output needs it). Remove the update, delete, search and get-by-email paths and the simulated delays.
- Reduce the DTOs and `User` to the fields the scenario prints; drop the data annotations.
- Shrink `IUserDataProvider` to match.
- Keep the console output readable and keep `docs/Examples.md` in sync.

## Acceptance criteria

- [ ] `dotnet run --project example/Demo.ConsoleApp` still shows the registration log, the lifetime comparison and the cross-scope user scenario.
- [ ] Every remaining class either carries `[AutoRegister]`, is a bootstrap or `AssemblyReference` file, or is needed by the scenario.
- [ ] `dotnet build AutoRegister.slnx` succeeds with no warnings, and the full test suite passes.
- [ ] `docs/Examples.md` snippets match the trimmed code.
