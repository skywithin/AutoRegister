## Context

Invalid configurations print a warning or error and skip the type: `RegisterAs` of `0`, a `serviceInterface` that isn't an interface or isn't implemented, or `RegisterAs.Interface` with no interface. The application starts normally and fails later, when the missing service is resolved, possibly in production and far from the cause. A misconfigured attribute is a programming error and should stop startup.

## Scope

- Collect every validation problem during a scan.
- Default for the new entry point: throw one `AutoRegisterConfigurationException` (or `InvalidOperationException`) that lists every problem with the type name.
- Add an option to keep today's behaviour (log and skip).
- Fold in the review's edge cases so they are reported consistently instead of crashing or being ignored:
  - a `null` assembly in the list (currently a `NullReferenceException`);
  - an undefined `Lifetime` value (currently throws `ArgumentOutOfRangeException` partway through registration);
  - undefined `RegisterAs` bits (currently registers nothing and still counts the type);
  - `serviceInterface` given without `RegisterAs.Interface` (currently silently ignored).
- Decide whether a `ReflectionTypeLoadException` should be reported this way or handled by scanning the types that did load.

## Acceptance criteria

- [ ] With the default mode, any invalid attribute makes the call throw before anything is registered, and the message names every offending type.
- [ ] With the lenient mode, behaviour matches today's (log and skip).
- [ ] Tests cover each validation rule in both modes.
- [ ] `dotnet build` and the full test suite pass.
- [ ] README and `docs/` updated: API-Reference "Exceptions" and Troubleshooting.

## Decision points

- Exception type: a custom exception, or `InvalidOperationException` with an aggregated message.
- Whether the legacy entry point adopts fail-fast in the major version, or stays lenient.
- Whether "no interface to register" is an error or stays a warning when `Self` is also set.
