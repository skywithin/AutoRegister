## Context

The only workflows are tag-triggered release pipelines (`build-and-publish.yml` on `v*`, `pre-release-publish.yml` on `rc-v*`). Nothing builds or tests the code on push or pull request, so a broken build is only discovered when a release tag is pushed. That is how the Swashbuckle 10 upgrade (commit `cd36a21`) broke the solution build on `main` and silently blocked every release until it was fixed by hand.

## Scope

- Add `.github/workflows/ci.yml`, triggered on `push` to `main` and on `pull_request` targeting `main`.
- Steps: checkout, `actions/setup-dotnet` with `10.0.x`, `dotnet restore AutoRegister.slnx`, `dotnet build AutoRegister.slnx -c Release --no-restore`, `dotnet test tests/AutoRegister.DI.Tests/AutoRegister.DI.Tests.csproj -c Release --no-build`.
- Build the whole solution (library, tests and example), so a broken example fails CI the same way it fails a release.
- Least-privilege token: `permissions: contents: read`.
- `concurrency` group per ref with `cancel-in-progress: true`, so superseded pushes stop running.
- No packing or publishing; this workflow never needs the NuGet API key.
- Add a CI status badge to `README.md`.

## Acceptance criteria

- [ ] A push to `main` and a pull request against `main` each run the workflow.
- [ ] The workflow fails when the solution build or any test fails.
- [ ] The workflow has a `permissions` block and a `concurrency` group, and uses no secrets.
- [ ] `README.md` shows the CI badge.
- [ ] `CLAUDE.md` Releases section mentions the CI workflow.

## Locations

- `.github/workflows/ci.yml` (new)
- `README.md`, `CLAUDE.md`

## Decision points

- Whether to also run `dotnet pack` (without pushing) so packaging errors surface before a tag. It is cheap and catches csproj/metadata mistakes; recommended.
- Whether to make the check required via branch protection on `main`. That is a GitHub repository setting, not a file change, so it is out of scope here but worth doing once the workflow exists.

## Related

Other release-workflow findings from the project review, to be filed separately:

- Release builds don't pass the version, so the packed DLL reports 1.0.0.
- `workflow_dispatch` on the stable workflow derives the version `refs/heads/main`.
- The release workflows lack a `permissions` block, pin actions only to major tags, put the API key on the command line, and are about 90% duplicated.
